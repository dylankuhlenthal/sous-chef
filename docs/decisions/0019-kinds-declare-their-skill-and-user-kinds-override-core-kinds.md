# 0019: Kinds declare their skill, sous chef refuses a missing one, and user kinds override core kinds

**Date:** 2026-09-30
**Status:** Accepted

## Context
Four of sous chef's six kinds (`shape`, `build`, `mega-shape`, `orchestrate`) tell the session to run one of the first owner's own skills. A teammate without those skills could spawn such a session, and it would start and then flounder, because nothing checked the skill first. Kinds were also read only from `kinds/` in the code, so the only way to add or change a kind was to edit the core's files. The goal (the second of three changes to make sous chef shareable) is that a teammate can run sous chef with whatever skills they have: a kind whose skill they lack is refused at spawn with a clear message, and they can add their own kinds or replace a built-in one without editing the core. The first owner's sous chef keeps behaving as before.

## Decision
**User kinds are looked up before core kinds.** User kinds live in `kinds/` under sous chef's data home (`util.home()`); core kinds in `kinds/` under the code root. A user kind replaces a core kind of the same name as a whole file. When both are the same folder, as today, it is the core only, so nothing changes for the first owner. A later change (splitting the core and the owner's data into separate repos) points the data home at the owner's personal folder, whose `kinds/` then becomes the user kinds with no code change. A separately named folder such as `my-kinds/` was set aside: a second name for the same idea, which that later change would likely move again.

**A kind declares the one skill it runs, and the runtime says whether it is there.** `skill: <name>` in the front matter. The runtime answers `skill_available(name, cwd)` with found, missing or cannot tell; only a definite "missing" refuses, before anything is written. The Claude runtime looks for the skill's files everywhere Claude Code reads skills from disk, and does not check names with a colon; a kind that relies on a skill it cannot see declares the namespaced name, which is not checked. There is no flag to skip the check: a wrong refusal is fixed in the runtime's check, and a user kind of the same name is the workaround meanwhile. Set aside: asking a real Claude session to list its skills (a model call per spawn, with no machine-readable answer), and not checking at all while telling the session to report `blocked` (the floundering case this change is about). The brief's `blocked` rule stays as a backstop for what the check cannot see.

**The core ships only kinds that need no skills: `general` and `investigate`.** `shape`, `build`, `mega-shape` and `orchestrate` are the first owner's user kinds; they stay in `kinds/` until the split of the core and the owner's data into separate repos moves them to the owner's side. Teammates who want them add them as their own user kinds. The owner's reason: sous chef should stay general; engineering teammates can add shape, build and the rest as user kinds, and teammates outside engineering do not need them. Keeping all six in the core was set aside, as was a core `shape` that runs `/shape` with `shape-gui` as the owner's override.

## Consequences
`sc kinds` shows each kind's skill, whether it is found, and whether the kind is a user kind; it cannot see project skills, because it has no working directory, so it may show a project-only skill as not found although a spawn into that project succeeds. `sc cron add` refuses a worker job whose skill is missing; a skill that goes missing later makes the job fail when it fires. A kind name must be lowercase kebab-case, which also stops `--kind` from reading outside the kinds folders. How it works: "Kinds" in `docs/domains/sessions.md`; how to add one: `docs/patterns/adding-a-kind.md`.
