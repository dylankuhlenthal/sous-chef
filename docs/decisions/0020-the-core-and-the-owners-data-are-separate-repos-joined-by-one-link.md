# 0020: The core and the owner's data are separate repos, joined by one link

**Date:** 2026-09-30
**Status:** Accepted

## Context
Until now sous chef's code and its first owner's data (memory, cron jobs, kinds, settings, session records) lived in one folder and one git repo. A teammate could not install it without taking the first owner's memory, and the repo could not be published: 116 of its 172 commits touch memory. The goal (TRV-1147, the last of three changes to make sous chef shareable) is that a teammate installs sous chef with one script and runs it as their own, with their data in a folder they choose (their own private git repo if they want one); that the core can be published with nothing personal in its files or history; and that the first owner's sous chef keeps running through the switch-over with the same memory, sessions, cron jobs, Slack and conversation. The rule the first owner set for all three sharing changes: the core names nothing specific to them; everything that is moves into their data.

## Decision
**Two repos.** The first owner's GitHub repo was renamed to `my-sous-chef` (private, full history) and becomes their data repo; the core is a new `sous-chef` repo whose history starts with one fresh commit. Rewriting the old repo's history was set aside: GitHub keeps pull request refs (`refs/pull/N/head`) through a force-push, so the memory would stay reachable. The switch-over is the only thing that ever pushes to the core, and it refuses unless the core repo is empty and the staged core has exactly one commit, because after the rename the old address reaches the new core and a push of any branch of the old folder would publish its whole history.

**One link.** The core stays at `~/.sous-chef` (Claude Code's trust, its saved conversations, the `~/.local/bin` links and every brief's `sc` path are keyed to it); the data folder is wherever the owner chose, by default `~/.my-sous-chef`. The core reaches it through one gitignored link, `<core>/my`. `util.home()` returns that path through the link, not resolved, so report paths in briefs stay valid if the data folder moves and the link is re-pointed. An environment variable was set aside, because background sessions can start with a stale environment; so were per-file links, because one forgotten link writes personal content into the shared repo.

**No link, no data.** Without a usable link, `sc` refuses and names the fix (run `install.sh`; the link's missing target; or the old combined layout, to be switched over). Help, the hooks and `sc setup` work without it. Falling back to the code folder, as before, was set aside: it would write a teammate's memory into ignored folders of the shared clone. Worktree detection moved to the code folder, since a worktree of the core has no link.

**The owner's own instructions live in the data folder, in two files.** `my/instructions.md` holds the owner's rules for sous chef, shown in full in the startup summary right after the owner line (with its own limit of 12,000 characters, and the summary's total limit raised by the same amount, from 30,000 to 42,000, because the summary is cut from the end where memory is). `my/worker-instructions.md` holds their rules for every session and goes into each brief, between the kind's instructions and the task, and is left out when empty. `AGENTS.md` and the brief template keep only general rules; every line that named a tool, service, repo, skill or kind only the first owner uses moved into these files. A Claude Code `@import` in `AGENTS.md` was set aside (specific to Claude Code, asks to approve an external import, behaviour with a missing file undocumented), as was folding the rules into memory files (capped, and notes rather than rules).

**Install by script; the logic in `sc`.** `install.sh` only checks `python3`, `git` and `claude` and runs `sc setup`, which makes or connects the data folder, asks for the owner when there is none, offers git and a push to an empty repo the owner made (it never creates repos), and makes the links. The logic lives in `sc` so the black-box tests cover it.

**The watcher keeps the data folder pushed.** When the data folder is a git repo with an upstream, the watcher commits after two quiet minutes, rebases and pushes, never force-pushes, and stops with an event that wakes sous chef on a conflict or five failed pushes in a row, starting again by itself once the conflict is resolved or the remote answers.

**`docs/decisions/` keeps the first owner's name.** These records say who decided what; rewording them would make them less true. The check that the core names nobody searches everything on the core's path list except this folder (and the search's own file). Two stored values from before the owner was a setting remain in the code as named constants, because the first owner's existing records still contain them.

## Consequences
A fresh clone of the core runs nothing until `install.sh` has made the link. Tests run against a temporary data folder (`SC_TEST_HOME`), and tests that copy the code copy only the core's path list, so the suite passes in the core as published. The first owner's switch-over is a one-off script kept in the data repo's history, rehearsed on a copy first. How it works: "Two folders joined by one link" in `docs/architecture.md`; installing: `docs/operations/running.md`; syncing: check 9 in `docs/domains/watcher.md`.
